# 開発ルール

- `.env` は直接編集せず、シークレットマネージャー参照のテンプレートから生成する運用を優先する。
- 大量出力（diff、ログ、JSON）は親コンテキストに流さず、必要ならサブエージェントやスクリプトで処理して要約だけ受け取る。**ただし通読が必要な品質レビューは委譲しない**（原稿全体の一貫性チェック、章をまたいだ表現重複、自分の設定ファイル群の見直しなど）。分割委譲すると章間の繰り返しや直し漏れが視界から外れる。

## Code Style Guidelines

- コードコメントは一切書かないでください
- 不要な空白は削除してください
- 新規ファイルを作成する際は必ず末尾に改行を足すこと

## GitHub Operations

- GitHubのリソース（リポジトリ、Issue、PR、コード等）を操作する際は、`gh` コマンド（GitHub CLI）を使用する
- WebFetchやWebSearchではなく、`gh` コマンドを優先する

## Development Philosophy

### Before Implementation

- 新しい機能を実装する前に、以下を必ず確認する：
  1. 既存のコードベース内に同様の実装やユーティリティがないか検索する
  2. 使用しているライブラリ/フレームワークに該当する API や機能がないか確認する
- 「自分で実装する」より「既存の解決策を使う」を優先する

### Test-Driven Development (TDD)

- 原則としてt-wadaのテスト駆動開発（TDD）で進める

### 日本語 Markdown の機械検査

日本語を書くときだけ踏む罠が3つある。いずれも目視では拾えないので、書いた直後に機械検査する。

**① 太字が全角約物の隣で壊れる。** 日本語で太字（`**`）を書くときは、太字の範囲を全角約物（`（）「」『』【】、。！？`等）の手前で切る。太字の内側の先頭・末尾に約物が来ると、CommonMark の flanking 判定で `**` が記号として認識されず画面にそのまま出る。

- 安全形: `**前者**（冒頭に立てる）を採りました`
- 崩れる形: `**前者（冒頭に立てる）**を採りました`

約物を太字に含めたいときだけ、閉じ `**` の直後に半角スペースを足す。

**② 長い日本語テキストにハングル・簡体字が1語だけ紛れ込む。** 見た目が漢字・かなに似ているため目視では拾えない。

```bash
rg -n '[가-힣一-鿿]' <file>.md | rg -v '[ぁ-んァ-ヶ]' | head
```

前段で CJK 全体を拾い、後段でかな交じり行（＝正常な日本語行）を落とす。残った行だけ目で見る。

**③ 外部へ投稿する Markdown は、投稿前に実際のパーサーへ通す。** 目視や正規表現より確実で速い。

```bash
npx --yes markdown-it <file>.md | grep -n '\*\*' && echo "崩れあり"
```

投稿後に気づいた場合は、コメントを削除して貼り直さず本文を差し替える（相手に通知が二重に飛ばない）。

## Chrome profile

- **ブラウザ自動操作には専用 profile を使い、通常利用の profile と認証状態を分離する。** これが既定。分離しておくと、エージェントの誤操作がユーザーの作業中のセッションへ波及しない。
- profile 名や接続先などの端末固有値はローカル設定で管理し、リポジトリへ保存しない。
- **タブの所有権はエージェントが作ったかどうかで決まる。** 自分が作っていないタブは、たとえ同じウィンドウにあっても画面遷移・URL 書き換え・再読込・閉じる操作をしない。エージェントは毎回、自分の作業用タブを新規作成する。
  - profile を分離していれば、この原則は自然に守られる。**利便性のために通常利用の profile を共有する運用を選んだ場合は、この所有権の判定だけが唯一の防御線になる**ので、より厳密に適用する。
- **フォーカスを奪う操作を原則禁止する。** 画面座標クリック、ウィンドウの前面化、アクティブタブの切り替え、ウィンドウのリサイズは、明示的に画面操作を依頼された場合を除いて行わない。認証・承認など前面操作が不可避なら、操作の直前で停止し、何を表示するかを通知してから了承を待つ。
- **自分が作ったタブは自分で閉じる。** URL パターンによる一括削除や、全タブを走査して条件で閉じるスクリプトは使わない。条件が正しくても、自分の管理外のタブを巻き込む。
- **予約・申請・送信などの完了画面は、スクリーンショットと要点を Markdown へ記録してから閉じる。** タブを開いたままにすることを記録の代わりにしない。ブラウザを閉じたら消える情報を、ブラウザに預けない。
- 認証・承認のタブは、認証が完了した時点で閉じる。


## ブラウザ操作ツールの優先順位

- **公式拡張（Claude in Chrome）をログイン済みブラウザ操作の既定にする**。接続先は決めた1つの profile に固定する。既存ウィンドウへバックグラウンドの作業タブを新規作成し、ユーザーの既存タブをclaimしない
- Claude Code の Chrome 連携は必要なセッションだけ `claude --chrome` または `/chrome` で有効にする。常時有効化は browser tools の context 消費が増えるため既定にしない
- コネクタ / CLI で扱える会社 SaaS はそちらを優先し、Chrome は UI 操作やログイン済み状態が必要な場合に使う
- **Chrome DevTools MCP は公式拡張へ完全移行済み**。MCP 本体も専用の CDP profile も削除した。**「フォールバックがある」前提で設計しない。** どうしても CDP 固有機能が要る場面に当たったら、その時点で MCP と profile を新規に用意し、まず公式拡張で代替できないかを検討する
- AgentCore Browser はローカル開発では使わない（AgentCore Runtime 上のエージェント用）
- **対象 profile のウィンドウが無ければ、確認なしに起動する。** 起動済みなら新しいウィンドウを増やさず、既存ウィンドウへ作業タブを作る。URLを付けた `open --new-window` は通常の入口に使わない。後片付けは公式拡張のタブグループ／tabIdを正として、自分が作ったタブだけを閉じる。URLパターンによる一括削除は、ユーザーのタブを巻き込むため使わない

### スマホ幅の検証に Chrome の窓を使わない

**Chrome のウィンドウは 606px までしか縮まず、390px の検証には使えない。本当の検証は iOS Simulator が正。** `resize_window` は tabId が属するウィンドウごと縮めるため、ユーザーが作業中の窓を縮める事故の原因になる。**打たない。** 既定スタイルシートで組んだ HTML なら、既知のハザード（表の `min-width`・固定px複数列グリッド・`nowrap` の乱用）を `rg` で静的に確かめれば足りる。

### ブラウザ操作テストではスクリーンショットを既定にしない

- **ブラウザ操作のテストではスクリーンショットを取得しない。** DOM、アクセシビリティツリー、URL、コンソール、ネットワーク応答、テストのアサーションで結果を検証する。
- 見た目の崩れなど画像でしか判定できない問題、またはユーザーが画像による確認・証跡を明示的に求めた場合だけ取得する。取得範囲は自分が作成したテスト用タブまたは対象要素に限定し、画面全体を含めない。
- テストフレームワークの失敗時自動撮影は既定で無効にする。必要な場合は保存先と保持期間を決め、認証情報・個人情報・他のタブが写らないことを確認する。

## `screencapture` は必ず範囲指定で撮る（画面全体を撮らない）

**エージェント自身の検証で `screencapture` を使うとき、引数なしの全画面撮影をしない。** ユーザーは並行して自分の作業をしているので、メール・Slack・顧客資料・チャットの中身がそのまま写る。見る必要のない情報を読み込むことになり、機密の観点でも良くない。

```bash
screencapture -x -R0,0,1710,30 out.png   # メニューバーだけ
```

- `-x` はシャッター音を鳴らさない。**常に付ける**
- `-R x,y,w,h` は**論理座標**（Retina では撮影結果が2倍のピクセル数で返る）。範囲がずれたら、返ってきた画像サイズと指定幅の比からスケールを割り出して計算し直す
- **アプリのウィンドウだけを撮りたいが位置を特定できない場合は、撮影自体を諦める。** ウィンドウ位置の取得には System Events のアクセシビリティ権限が要り、無音のダイアログを踏む。ユーザーに画面を見てもらうほうが速くて安全
- 誤って撮ってしまったら、**その場でファイルを削除し、写っていた内容には触れない**


## 基本

- コンテキスト節約のため、調査やデバッグにはサブエージェントを活用する。ただし**通読が必要な品質レビューは委譲しない**（原稿全体のAI臭・一貫性チェック、図版の挿入位置の妥当性、自分の設定ファイルの見直し等）。正本は `~/.claude/AGENTS.md`「開発ルール」節
- 開発中に生成するドキュメントに API キー等の機密情報を書く場合は、必ず .gitignore に追加する
- 「変更不要」「問題なし」と結論する前に、必ずその根拠を明示する。ドキュメントやソースを確認せずに「正確です」と言わない
- **全体スコープへの断定**（「このコードベースには〜がない」等）は、必ず `grep -rn` で全ファイル横断スキャンしてから言い切る。一部のファイルだけ見て全体を断定しない
- **1件の指摘は、そのクラス全体の指摘として受け取る。** 「p.228 のキャプションが無い」「4章の扉がはみ出している」と言われたら、直すのは指摘された1件ではなく、**同じ条件に当てはまる全箇所**。直す前に `grep` / スクリプトで全該当箇所を機械的に列挙し、その一覧を報告に載せる。ただし**広げるのは「不備の判定条件」であって「直し方の値」ではない**。「小さすぎる」と言われて下限だけの検査を書くと、元から適正だった箇所まで持ち上げて反対側へ振り切る。**下限を作ったら上限も同時に持ち、元の値のままで条件を満たす箇所は触らない**
- **直すのは指摘された不備だけ。ついでに気になった要素を巻き込まない。** 同じページ・同じファイルにあっても、指摘されていない文字・ロゴ・IDの位置や有無は**元のまま残す**。直す前に元の値を控え、変更した要素を報告に列挙する
- **「◯件ある」と要約する前に、必ず全件を列挙して検算する。** 目視で数えた件数は外れる。列挙できたなら、その検査自体をスクリプト化してリポジトリへ残す——同じ穴は次のUI更新・次の章で必ず再発する
- 判定一覧を出すときは、各行の**根拠の信頼度**（実コード確認 / ドキュメント確認 / 主観 / 推測）を明示する
- パッケージ・ライブラリを選定するときは、選んだ理由と代替案を必ず示す
- WebFetch で URL 本文が取得できない場合（JS 描画ページ等）は、推測で進めずユーザーに本文のコピペを依頼する
- **外部から提供された手順書・設定ファイルに書かれたAPIエンドポイント等の接続先情報を鵜呑みにしない**。認証エラー（Invalid token等）が出たら、認証情報自体だけでなく「接続先が正しい環境（Sandbox/Prod等）を向いているか」も早い段階で疑う。method解決が成功する（Method not found にならない）ことは「エンドポイントが生きている」証拠にはなるが「正しい環境である」証拠にはならない（Sandbox環境にも同じAPI実装が存在しうるため）。深追いする前に、ツール作者・提供元に接続先URLの一次確認を取るのが早い

## 確認していないことを、確認した形で言わない

**「たぶんこうです」を「こうです」に丸めない。** 断定してよいのは、自分でその一次情報を読んだときだけ。読んでいないなら文中に「未確認」と書くか、先に読んでから答える。どちらもできない項目は報告に載せない。

- **件数・分類・状態は、全件を1件ずつ読んでから言う。** 「20件が古いテストの残骸」のようなまとまった判定は、サンプルや命名規則からの推測で作られやすい。全件読むコストが高いなら「N件中M件を確認した。残りは未確認」と分数で書く
- **エラーで見られなかった経路は「無かった」に含めない。** 認証切れ・権限不足で開けなかった場所は、開けなかったことを報告に明記する。401 を踏んだまま「記録なし」と結論しない
- **他人の資料に書いてある事実も、裏取りするまで自分の結論にしない。** 提案書・議事録・台帳の記載は「その文書にそう書かれている」であって事実確認済みではない。外へ出す文へ引き写す前に、出所を全文検索で確かめる
- **既にある値を「誤記に見える」を理由に書き換えない。** 台帳・メモ・設定に入っている数字や表記が不自然でも、直すのは**元メール・注文控え・公式ページなどの一次情報と突き合わせたときだけ**。合わないまま残すほうが、静かに直して合っているように見せるより安全
- **本番システムの調査では特に厳しく適用する。** 推測から作った手順は、実行したあとに間違いが分かる

## 待ち時間の正体はツールの往復回数（実測）

**ユーザーが「遅い」と言うとき、遅いのはコマンドではなくコマンドとコマンドの間である。**
長期プロジェクトの直近80セッション分のログ（293MB）を集計して確かめた結果は次のとおり：

- あるセッションの21分のうち、**モデルの応答が14.7分（81%）**。コマンドの実行は合計3.4分で、
  Bash 1回あたり平均3.7秒しかかかっていない
- **1回あたりの速度は3週間まったく変わっていない**（Opus 5 の応答は中央値8秒前後、Bashは2.2秒で横ばい）。
  増えたのは**回数**で、7月末は1日136回だったBashが8/15には630回、待ちの合計は178分になっていた
- 短いコマンド42回だけで5.7分。**1回8秒でも、回数が積むと分単位になる**

**だから速くする方法は1つで、往復の回数を減らすこと。** 1回あたりを速くしようとしても効かない。

- **副作用のない調査は目的単位で1コマンドにまとめる。**「1つの問いにつき1コマンド」にしない。
  リポジトリの状態を掴むなら `git log`・`ls`・`grep` を1回の呼び出しへ束ね、区切りの `echo` で見出しを付ける
- **検査・検算も束ねる。** 個別に走らせず、NGだけを出力する形にまとめる
- **重い処理は `run_in_background` で先に走らせ、待つ間に別の作業を進める。**
  ビルド・デプロイ・大きな変換は、開始してから成果物づくりへ移る。最後にまとめて待たない
- **長いスクリプトを1回で書くのは、細かく刻むより速い。** 出力が長い回は確かに遅くなるが（11,000字で78秒）、
  同じ処理を5回に割ると往復5回分の思考時間が乗る
- **⚠️ 安全のための分割は往復削減の対象外。** `git diff` で確認してから `git add` する、
  外部発信の前に承認を挟む、といった分割は維持する（下の「複数作業の混線防止」節）。
  束ねてよいのは**副作用のない読み取りだけ**

## 大規模出力を親コンテキストに取り込まない（`Prompt is too long` 対策）

`git diff` 生パッチ・大量 grep 結果・PDF 全文・長大ログ等を親のメッセージ履歴に直接流し込まない。親の膨張は後続ツール呼び出しやサブエージェント起動プロンプトに波及し、MCP 定義が重い環境では特に上限超過しやすい。

| 出力の目安 | 処理方針 |
|-----------|---------|
| 500 行未満 / 数十KB 以下 | 親で直接読んで OK |
| 500 行以上 / 数百KB 以上 / 数十ファイル分の diff / PDF 30ページ超 | サブエージェント（general-purpose）に委譲し、要約・判定結果（表・JSON）だけ受け取る |

サブエージェント委譲の作法：

- プロンプトは**自己完結**で書く（「親のコンテキストを参照」と書かず、必要な情報・ルールを再掲する）
- 戻り値はフォーマット固定（JSON / 表）にして生データを返させない。並列時は戻り値の合計サイズも指定する（例：上位N件・1件200字以内）
- 編集・コミット等の副作用のある操作は親が担当し、子は読み取り・分析に限定する


## サブエージェント並列起動は原則逐次

「MCP 定義が重い環境 × 親コンテキストの膨張 × 複数並列」が揃うと `Prompt is too long` で即失敗する。

対策の優先順：①並列をやめて逐次処理（完走確実性優先）②親のコンテキストを事前に軽くする ③子に渡す prompt を簡潔にする ④どうしても並列なら 2〜3 個まで。

スキルで Agent 並列起動を設計するときは、SKILL.md に「並列化できる根拠」を明記する。根拠がなければデフォルトで逐次。

## 「調べつくして」系の網羅指示で、無断の大規模ファンアウトをしない

ユーザーの「調べつくして」「徹底的に」「網羅的に」「全部洗い出して」は、**規模の白紙委任ではない**。高性能モデル（Fable / Mythos 級）のセッションでこれを字義どおり受けてサブエージェントや Workflow を大量並列で撒くと、子は親と同じモデルを継承するため**トークン消費が桁で膨らみ、レートリミットに当たってセッションごと止まる**。網羅の徹底度を上げる前に、まず消費の見積もりを出す。

- **4体以上のサブエージェント起動、または Workflow による多段オーケストレーションを始める前に、計画の規模を1〜2行で提示して確認を取る**（例:「観点5系統×検証2巡で最大15エージェント回します。消費が大きいですが進めますか？ 逐次3体の縮小版もあります」）。3体以下の逐次・小規模並列は従来どおり確認不要。
- 確認なしで進めてよいのは、**ユーザーが規模を明示したとき**（「エージェント10体で」「ultracode で」「+500k で」等）だけ。「調べつくして」は徹底度の指示であって規模の指示ではない。
- 縮小版を設計するときの優先順は上の「サブエージェント並列起動は原則逐次」節と同じ。加えて、機械的な収集・整形ステージは `model: haiku` / `sonnet` へ落とし、親モデル継承のまま撒かない。
- レートリミットに当たってからの分割リトライは、消費をさらに積むだけなので回復手段にしない。当たったら残作業を報告して指示を待つ。

## perl / sed 一括置換の `|` エスケープ漏れ事故

`perl -pi -e 's/| foo | bar |/.../'` のように**パターン先頭・中間の `|` を未エスケープ**にすると、正規表現の交替（alternation）として解釈され**空文字列にもマッチ → 全行の行頭に置換文字列が挿入**される大事故になる。

- Markdown テーブル行など `|` を含む置換は **`\|` に全てエスケープ**するか、**Edit ツール / Python スクリプトを使う**（確実）
- **一括置換後は必ず `head` / `git diff` で対象ファイルの構造を目視確認**する。置換の exit code だけで成功と判断しない
- **「意図した箇所以外は1文字も変わっていない」を機械で証明する**。目視は差分が多いと破綻する。置換対象（コメント・タグ等）を正規表現で除去して正規化したテキストを、`git show HEAD:<path>` の版と全ファイル比較し、差分ゼロを確認する。これなら数十ファイル・数百行の変更でも巻き込み事故を確実に検出できる（本文中のTODOコメント48件を一括整理したときに有効だった）
- 複数ファイルへの機械置換後は「同一行頭が多数行で繰り返される」「テーブル断片と見出しが同一行に混在」等の壊れパターンを grep で検査する

## 「機械検証した」と言う前に、その検証が対象を読んでいることを壊した検体で確かめる

**検証コードが対象の一部を素通りしていると、出力は「差分なし＝合格」と区別が付かない。** 沈黙は「問題がない」ではなく「見ていない」かもしれない、を既定の疑いにする。**検証を書いたら、わざと1文字変えた検体を食わせて、それが検出されることを先に確かめてから合格判定に使う。**

- 落ちやすいのは**入れ子の中身**。pptx の表セル・グループ内図形、docx の表・ヘッダー、HTML の iframe・shadow DOM、JSON のネストした配列。トップレベルの走査だけで「全部見た」と思い込む
- **「N件検出した」ではなく「N件中M件を走査した」を出力する検証にする。** 走査数が想定より少ないことは、差分ゼロより雄弁に穴を教える
- 報告に「完全一致を機械照合済み」と書くときは、**何を照合したかを具体的に併記する**（「テキスト・座標・色・サイズ」など）。書けないなら、まだ照合できていない

## 一覧APIは「全部取れた」を自分で確かめる。既定の上限で静かに切れる

Confluence / Drive / Gmail / Slack などの一覧APIは、**指定しなければ既定の件数（25・50・100）で打ち切る**。打ち切られた出力は件数が少ないだけの出力と見分けがつかず、そのまま「これが全部」と扱うと最新版を取りこぼしたまま古い資料を正本にする。

- **件数を先に数える。** `limit` を明示し、レスポンスの `_links.next` / `nextPageToken` / `totalSize` を見て続きが無いことを確認してから中身の判断に入る
- **「N件中M件を見た」を報告に書く。** 「該当の資料はこれです」ではなく「添付37件を全件見て、本文から参照されているのはこの1件」と書けば、打ち切りに自分で気づける
- **本文からの参照と突き合わせる。** 本文がリンクしていない添付はたいてい旧版。逆に本文が参照しているのに一覧に無いなら、それが打ち切りの証拠

## zsh の glob 失敗はコマンド全体を中断させる（検証の偽陰性）

zsh はマッチしない glob（例: `references/*.md` が存在しないディレクトリ）があると `no matches found` で**コマンド全体を実行せず中断**する。`2>/dev/null` では防げない。grep 検証にこれが混ざると「grep が実行されなかった」のに「マッチなし＝未収載」と誤判定する偽陰性事故になる。

- 存在が不確かなパスの glob は使わず、**ディレクトリごとに個別実行**するか `grep -r <dir>/` でディレクトリ再帰にする
- どうしても glob を使うなら `setopt null_glob` か `ls <glob> 2>/dev/null` で先に存在確認する
- **「無し」と断定する前に、検証コマンド自体が実行されたか（エラー出力の有無）を確認する**
- 同系統の罠：zsh は `=` で始まる裸のワードを `=command` 展開（コマンドのパス解決）するため、`echo ===` のような区切り線出力が `== not found` で**コマンド全体を中断**させる。区切り線は `echo "==="` とクォートするか `---` を使う
- 同系統の罠：**`GID` / `UID` / `EUID` / `EGID` をシェル変数として使わない。** zsh ではこれらがプロセスのグループID・ユーザーIDを指す特殊変数なので、`SHEET_GID=$(cat gid.txt)` の意味で `GID=$(...)` と書くと **`failed to change group ID: operation not permitted` でコマンド全体が実行されない**。エラー文がシェルの権限問題のように見えるため、直前のヒアドキュメントやリダイレクトを疑って時間を失う。IDを入れる変数は `SHEET_GID` のように接頭辞を付ける
- 同系統の罠：**zsh は引用符なしの変数をスペースで分割しない。** `REGIONS=$(aws ec2 describe-regions … --output text)` を `for R in $REGIONS` で回すと、17リージョンが1語のままループが1回だけ回り、全件エラー＝「全リージョン無効」と誤判定する。**`for R in $(aws …)` とコマンド置換を直接書く**（置換の結果は分割される）か、`${=REGIONS}` と書く
- 同系統の罠：**`$VAR:` の直後に英字を続けない。** zsh では `:r` `:h` `:t` `:e` などが変数修飾子なので、`"arn:aws:iam::$ACC:role/…"` が `:r`（拡張子を取る）と解釈されて ARN が壊れる。**ARN やパスを組み立てるときは必ず `${ACC}` と波括弧で括る**
- 同系統の罠：`grep -rn … --include=*.md` のように**オプション値の glob を裸で書く**と zsh が展開を試み、`no matches found: --include=*.md` でコマンド全体が中断する。`--include='*.md'` とクォートするか、対象ディレクトリ指定の再帰 grep に切り替える

## 設定ディレクトリをシンボリックリンクにしていると、検索の書き方しだいで静かに空振りする

`~/.claude/` 配下を dotfiles リポジトリへのシンボリックリンクで管理している場合、**検索コマンドはリンクの扱いが実装ごとに違い、外すとエラーも警告も出さず終了コード1（＝該当なし）で返る**ので、本物の「該当なし」と区別が付かない。

| 検索の書き方 | `/usr/bin/grep -r` | `rg` |
|---|---|---|
| `~/.claude/AGENTS.md`（リンクの**ファイル**を引数指定） | ❌ 0件 | ✅ |
| `~/.claude/rules`（リンクの**ディレクトリ**。末尾スラッシュ無し） | ❌ 0件 | ✅ |
| `~/.claude/rules/`（末尾スラッシュあり） | ✅ | ✅ |
| `~/.claude/`（**リンクを含む親を再帰**） | ❌ 素通り | ❌ 素通り（`rg -L` なら読む） |

- **具体パスを引数に指定して `rg` で引く**のが既定。`~/.claude/` を丸ごと再帰するなら **`rg -L`** が要る。最も確実なのはリンク先の実体を直接見ること
- 対話シェルの `grep` がエイリアスや関数で別実装に置き換わっていると、**同じコマンドがサブエージェントや非対話実行では `/usr/bin/grep` に解決されて結果が変わる**ので、手元で通ったことを根拠にしない。**`rg` に `--include` は無い**点も同様の落とし穴（`-g '*.md'` / `-t md` を使う）
- **0件を「無い」の根拠にする前に、必ず存在するはずの語で1回引いて、検索が対象を読んでいることを確かめる**

## 複数作業の混線防止（CWD 干渉・ステージ範囲）

- Bash の並列実行間でも **working directory は共有される**。片方の `cd` がもう片方の git 操作先を変えてしまう事故実績あり。`cd` を使わず **`git -C <path>`** でリポを明示し、異なるリポの更新を同一メッセージで並列にしない
- `git add -A` / `git add <dir>/` / `git add -u <dir>/` は**並行セッションの未コミットファイルを巻き込む**（`-u` は「追跡済みだけだから安全」に見えるが、ディレクトリ指定なら巻き込み方は同じ）。対策の優先順：
  1. 自分が触ったファイルパスを明示列挙して add する
  2. `git commit <path> -m "..."` でパス指定コミット（最も確実。**ただし `git add` で明示列挙した場合に限る。`git apply --cached` で絞った直後には使わない**→下記）
  3. コミット前に `git status --short <dir>/` で目視。見覚えのないファイルは別セッションの作業
  4. `git add -A` / `git add <dir>/` / `git add -u <dir>/` は「自分しか触っていない」と確信できるときだけ
  5. 削除をstageしたいときも `git add <消したファイルの明示パス>` で足りる（`git add -u` のディレクトリ指定へ逃げない）
- ⚠️ **複数セッションが同じファイルへ1行ずつ足す「共有台帳ファイル」は、パスを明示列挙しても巻き込みを防げない。** 代表例は、成果物やページの登録先になっている YAML・案件の索引 `README.md` など、並行セッションがそれぞれ1行ずつ追記していくファイル。**ルール・設定ファイル（`CLAUDE.md` / `AGENTS.md` / `.claude/rules/*.md` / スキルの `SKILL.md`）も同じ扱いにする。**複数セッションへ同時に「学習しといて」と頼むと、学びの追記先は衝突しやすい。ファイル単位で add すると、別セッションが書いた行まで巻き込んで push してしまう（データは失われないが、相手のセッションからは自分の未コミット分が消えたように見える）。ファイル単位でstageする以上、他セッションの未コミット行も一緒に入る。**この種のファイルは、add の直前に `git diff <path>` を読んで自分の変更だけかを確かめる**。混ざっていた場合、`git add -p` は対話式なのでエージェントからは使えない。**`-U0` で変更行ごとに分割してから、自分の分だけ `git apply --cached` する**：

```bash
git diff -U0 <path> > /tmp/all.patch   # 文脈行なし＝変更行ごとに別のかたまりになる
# ヘッダー（--- / +++ まで）＋ 自分の変更のかたまりだけを抜き出して /tmp/mine.patch を作る
git apply --cached --unidiff-zero /tmp/mine.patch
git diff --cached <path>                # 自分の変更だけが stage されたか目で確認
```

⚠️ **既定の `git diff`（文脈3行）だと、近い行の変更が1つのかたまりに合流して分離できない**。必ず `-U0` を使い、`git apply` 側にも `--unidiff-zero` を付ける。分離できなければ、そのファイルは**コミットせず相手に委ねる**（publish 等で成果物へ反映済みなら実害はない）。無理に含めて報告するより、触らないほうが後始末が要らない。

⚠️ **`git apply --cached` で index を正しく絞っても、直後に `git commit <path> -m "..."` を打つと台無しになる。** pathspec 付きの `git commit` は index を見ず、**その時点のワーキングツリーの内容をそのままコミットする**。絞ったはずの index が無視され、他セッションの未コミット分（ワーキングツリー上にまだ残っている）を丸ごと巻き込んで push する。`git apply --cached` の直後は、**pathspec を付けない `git commit -m "..."`**（index の状態がそのままコミットされる）を使う：

```bash
git apply --cached --unidiff-zero /tmp/mine.patch
git diff --cached <path>   # 自分の変更だけが stage されたか確認
git commit -m "..."        # ← ここで <path> を付けない。付けるとワーキングツリー全体に戻る
```


⚠️ **`git diff` での確認と `git add`〜`commit` を、同じ連結コマンド（`&&` つなぎ）に入れない。** 連結すると diff の出力を読む前に add が走り、「確認したつもりで巻き込む」形になる。diff は単独の Bash 呼び出しで実行し、出力を読んで自分の変更だけと確かめてから、次の呼び出しで add する。

⚠️ **復元に相対リビジョン（`HEAD~1` / `HEAD^` / `@{1}`）を使わない。コミットハッシュを明示する。** 自分が最後に見た `HEAD` は、並行セッションのコミットで既にずれている。`git log --oneline -5 -- <file>` で戻したい版のハッシュを確かめてから `git checkout <hash> -- <file>` を打つ。
