# 開発ルール

## 基本

- `.env` は直接編集せず、シークレットマネージャー参照のテンプレートから生成する運用を優先する。
- 開発中に生成するドキュメントに API キー等の機密情報を書く場合は、必ず .gitignore に追加する。
- 調査・デバッグや大量出力の処理はサブエージェントへ委譲し、要約だけ受け取る（詳細は「大規模出力を親コンテキストに取り込まない」節）。**ただし通読が必要な品質レビューは委譲しない**（原稿全体の一貫性、章をまたいだ表現重複、図版の挿入位置、自分の設定ファイル群の見直しなど）。分割すると章間の繰り返しや直し漏れが視界から外れる。
- **全体スコープへの断定**（「このコードベースには〜がない」等）は、全ファイル横断で検索してから言い切る。一部のファイルだけ見て全体を断定しない。
- **1件の指摘は、そのクラス全体の指摘として受け取る。** 直す前に `grep` / スクリプトで同じ条件に当てはまる全箇所を機械的に列挙し、その一覧を報告に載せる。ただし**広げるのは「不備の判定条件」であって「直し方の値」ではない**。下限を作ったら上限も同時に持ち、元の値のままで条件を満たす箇所は触らない。
- **直すのは指摘された不備だけ。** 同じファイルにあっても、指摘されていない要素は元のまま残す。直す前に元の値を控え、変更した要素を報告に列挙する。
- **「◯件ある」と要約する前に、全件を列挙して検算する。** 列挙できたなら、その検査自体をスクリプト化してリポジトリへ残す。
- 判定一覧を出すときは、各行の**根拠の信頼度**（実コード確認 / ドキュメント確認 / 主観 / 推測）を明示する。
- **外部から提供された手順書・設定の接続先情報を鵜呑みにしない。** 認証エラーが出たら、認証情報だけでなく接続先が正しい環境（Sandbox/Prod等）かも早い段階で疑う。method が解決できることは「正しい環境である」証拠にならない。深追いする前に提供元へ接続先 URL を確認する。

## コードスタイル

- コードコメントは書かない。
- 不要な空白は削除する。
- 新規ファイルの末尾には改行を入れる。

## GitHub 操作

- GitHub のリソース（リポジトリ、Issue、PR、コード等）は、WebFetch・WebSearch ではなく `gh` コマンドで操作する。

## 実装方針

- 新しい機能を実装する前に、既存のコードベース内の同様の実装・ユーティリティと、使用中のライブラリ/フレームワークの該当 API を確認する。自作より既存の解決策を優先する。
- 原則として t-wada のテスト駆動開発（TDD）で進める。

## 日本語 Markdown の機械検査

日本語で書くときだけ踏む罠が3つある。目視では拾えないので、書いた直後に機械検査する。

**① 太字が全角約物の隣で壊れる。** 太字（`**`）の範囲は全角約物（`（）「」『』【】、。！？`等）の手前で切る。太字の内側の先頭・末尾に約物が来ると、CommonMark の flanking 判定で `**` がそのまま表示される。

- 安全形: `**前者**（冒頭に立てる）を採りました`
- 崩れる形: `**前者（冒頭に立てる）**を採りました`

約物を太字に含めたいときだけ、閉じ `**` の直後に半角スペースを足す。

**② 長い日本語テキストにハングル・簡体字が1語だけ紛れ込む。**

```bash
rg -n '[가-힣一-鿿]' <file>.md | rg -v '[ぁ-んァ-ヶ]' | head
```

前段で CJK 全体を拾い、後段でかな交じり行を落とす。残った行だけ目で見る。

**③ 外部へ投稿する Markdown は、投稿前に実際のパーサーへ通す。**

```bash
npx --yes markdown-it <file>.md | grep -n '\*\*' && echo "崩れあり"
```

投稿後に気づいた場合は、削除して貼り直さず本文を差し替える（相手に通知が二重に飛ばない）。

## ブラウザ操作

### ツールの選択

- **公式拡張（Claude in Chrome）をログイン済みブラウザ操作の既定にする。** Chrome 連携は必要なセッションだけ `claude --chrome` または `/chrome` で有効にする（常時有効化は context 消費が増える）。
- コネクタ / CLI で扱える SaaS はそちらを優先し、Chrome は UI 操作やログイン済み状態が必要な場合に使う。
- Chrome DevTools MCP は導入していない。CDP 固有機能が必要になったら、まず公式拡張で代替できないかを検討する。
- AgentCore Browser はローカル開発では使わない（AgentCore Runtime 上のエージェント用）。

### profile とタブ

- **専用 profile を使い、通常利用の profile と認証状態を分離する。** 接続先は決めた1つの profile に固定し、profile 名などの端末固有値はローカル設定で管理してリポジトリへ保存しない。
- 対象 profile のウィンドウが無ければ確認なしに起動する。起動済みなら新しいウィンドウを増やさず、既存ウィンドウへ作業タブを作る。URL を付けた `open --new-window` は通常の入口に使わない。
- **タブの所有権はエージェントが作ったかどうかで決まる。** 毎回自分の作業用タブを新規作成し、自分が作っていないタブには遷移・URL 書き換え・再読込・閉じる操作をしない。通常利用の profile を共有する運用では、この判定が唯一の防御線になるので、より厳密に適用する。
- **自分が作ったタブは、タブグループ／tabId を正として自分で閉じる。** URL パターンによる一括削除や、全タブを走査して条件で閉じるスクリプトは、管理外のタブを巻き込むので使わない。認証・承認のタブは完了した時点で閉じる。
- **予約・申請・送信などの完了画面は、要点を Markdown へ記録してから閉じる。** タブを開いたままにすることを記録の代わりにしない。

### フォーカスと画面サイズ

- **フォーカスを奪う操作を原則禁止する。** 画面座標クリック、ウィンドウの前面化、アクティブタブの切り替え、ウィンドウのリサイズは、明示的に画面操作を依頼された場合を除いて行わない。認証・承認など前面操作が不可避なら、直前で停止し、何を表示するかを通知してから了承を待つ。
- **`resize_window` は使わない。** tabId が属するウィンドウごと縮めるため、ユーザーの作業中の窓を縮める。Chrome は 606px までしか縮まないので、スマホ幅（390px）の検証は iOS Simulator を正とする。既定スタイルシートで組んだ HTML なら、既知のハザード（表の `min-width`・固定px複数列グリッド・`nowrap` の乱用）を `rg` で静的に確かめれば足りる。

### スクリーンショット

- **ブラウザ操作のテストではスクリーンショットを取得しない。** DOM、アクセシビリティツリー、URL、コンソール、ネットワーク応答、テストのアサーションで検証する。
- 画像でしか判定できない問題、またはユーザーが画像による確認・証跡を明示的に求めた場合だけ取得する。範囲は自分が作成したテスト用タブまたは対象要素に限定する。
- テストフレームワークの失敗時自動撮影は既定で無効にする。必要な場合は保存先と保持期間を決め、認証情報・個人情報・他のタブが写らないことを確認する。

## `screencapture` は必ず範囲指定で撮る

**引数なしの全画面撮影をしない。** ユーザーが並行して作業している画面の内容（メール・Slack・顧客資料等）が写る。

```bash
screencapture -x -R0,0,1710,30 out.png   # メニューバーだけ
```

- `-x`（シャッター音なし）は**常に付ける**。
- `-R x,y,w,h` は**論理座標**（Retina では2倍のピクセル数で返る）。ずれたら返ってきた画像サイズと指定幅の比からスケールを計算し直す。
- **ウィンドウの位置を特定できない場合は、撮影自体を諦める。** 位置取得には System Events のアクセシビリティ権限が要り、無音のダイアログを踏む。
- 誤って撮ってしまったら、**その場でファイルを削除し、写っていた内容には触れない**。

## 確認していないことを、確認した形で言わない

**「たぶんこうです」を「こうです」に丸めない。** 断定してよいのは、自分でその一次情報を読んだときだけ。読んでいないなら「未確認」と書くか、先に読んでから答える。

- **件数・分類・状態は、全件を1件ずつ読んでから言う。** 全件読むコストが高いなら「N件中M件を確認した。残りは未確認」と分数で書く。
- **エラーで見られなかった経路は「無かった」に含めない。** 認証切れ・権限不足で開けなかった場所は報告に明記する。
- **他人の資料に書いてある事実も、裏取りするまで自分の結論にしない。** 外へ出す文へ引き写す前に出所を確かめる。
- **既にある値を「誤記に見える」を理由に書き換えない。** 直すのは一次情報（元メール・注文控え・公式ページ等）と突き合わせたときだけ。
- **本番システムの調査では特に厳しく適用する。**

## ツールの往復回数を減らす

待ち時間の大半はコマンドの実行ではなく、ツール呼び出しごとのモデルの応答である。速くするには往復の回数を減らす。

- **副作用のない調査は目的単位で1コマンドにまとめる。** `git log`・`ls`・`grep` などを1回の呼び出しへ束ね、区切りの `echo` で見出しを付ける。検査・検算も束ね、NG だけを出力する。
- **重い処理は `run_in_background` で先に走らせ、待つ間に別の作業を進める。**
- 長いスクリプトは細かく刻まず1回で書く。
- **⚠️ 安全のための分割は対象外。** `git diff` の確認と `git add`、外部発信前の承認などの分割は維持する。束ねてよいのは副作用のない読み取りだけ。

## 大規模出力を親コンテキストに取り込まない（`Prompt is too long` 対策）

`git diff` 生パッチ・大量 grep 結果・PDF 全文・長大ログ等を親のメッセージ履歴に直接流し込まない。

| 出力の目安 | 処理方針 |
|-----------|---------|
| 500 行未満 / 数十KB 以下 | 親で直接読んで OK |
| 500 行以上 / 数百KB 以上 / 数十ファイル分の diff / PDF 30ページ超 | サブエージェント（general-purpose）に委譲し、要約・判定結果（表・JSON）だけ受け取る |

サブエージェント委譲の作法：

- プロンプトは**自己完結**で書く（必要な情報・ルールを再掲する）。
- 戻り値はフォーマット固定（JSON / 表）にし、並列時は合計サイズも指定する（例：上位N件・1件200字以内）。
- 編集・コミット等の副作用のある操作は親が担当し、子は読み取り・分析に限定する。

## サブエージェント並列起動は原則逐次

MCP 定義が重い環境で親コンテキストが膨らんだまま複数並列にすると `Prompt is too long` で失敗する。

対策の優先順：①並列をやめて逐次処理 ②親のコンテキストを事前に軽くする ③子に渡す prompt を簡潔にする ④どうしても並列なら 2〜3 個まで。

スキルで Agent 並列起動を設計するときは、SKILL.md に「並列化できる根拠」を明記する。根拠がなければ逐次。

## 網羅指示で無断の大規模ファンアウトをしない

「調べつくして」「徹底的に」「網羅的に」は徹底度の指示であって、規模の白紙委任ではない。子は親のモデルを継承するため、大量並列はトークン消費が桁で膨らみ、レートリミットでセッションごと止まる。

- **4体以上のサブエージェント起動、または Workflow による多段オーケストレーションの前に、規模を1〜2行で提示して確認を取る**（例:「観点5系統×検証2巡で最大15エージェント回します。逐次3体の縮小版もあります」）。3体以下の逐次・小規模並列は確認不要。
- 確認なしで進めてよいのは、ユーザーが規模を明示したとき（「エージェント10体で」等）だけ。
- 機械的な収集・整形ステージは `model: haiku` / `sonnet` へ落とし、親モデル継承のまま撒かない。
- レートリミットに当たったら分割リトライせず、残作業を報告して指示を待つ。

## perl / sed 一括置換の `|` エスケープ漏れ事故

パターン中の `|` を未エスケープにすると交替（alternation）として解釈され、**空文字列にもマッチして全行の行頭に置換文字列が挿入**される。

- `|` を含む置換は **`\|` に全てエスケープ**するか、**Edit ツール / Python スクリプトを使う**。
- 一括置換後は `git diff` で構造を確認する。exit code だけで成功と判断しない。
- **「意図した箇所以外は1文字も変わっていない」を機械で証明する。** 置換対象を正規表現で除去して正規化したテキストを、`git show HEAD:<path>` の版と全ファイル比較し、差分ゼロを確認する。
- 複数ファイルへの機械置換後は「同一行頭が多数行で繰り返される」「テーブル断片と見出しが同一行に混在」等の壊れパターンを grep で検査する。

## 「機械検証した」と言う前に、壊した検体で確かめる

**検証コードが対象の一部を素通りしていると、「差分なし＝合格」と区別が付かない。** 検証を書いたら、わざと1文字変えた検体で検出されることを先に確かめてから合格判定に使う。

- 落ちやすいのは**入れ子の中身**（pptx の表セル・グループ内図形、docx の表・ヘッダー、HTML の iframe・shadow DOM、JSON のネストした配列）。
- **「N件中M件を走査した」を出力する検証にする。** 走査数が想定より少ないことが穴を教える。
- 「完全一致を機械照合済み」と書くときは、何を照合したか（テキスト・座標・色・サイズ等）を併記する。

## 一覧 API は「全部取れた」を自分で確かめる

一覧 API（Confluence / Drive / Gmail / Slack 等）は、指定しなければ既定の件数（25・50・100）で打ち切る。打ち切られた出力は件数が少ないだけの出力と見分けがつかない。

- **`limit` を明示し、`_links.next` / `nextPageToken` / `totalSize` で続きが無いことを確認してから判断する。**
- **「N件中M件を見た」を報告に書く。**
- **本文からの参照と突き合わせる。** 本文がリンクしていない添付はたいてい旧版。本文が参照しているのに一覧に無いなら打ち切りの証拠。

## zsh の glob 失敗はコマンド全体を中断させる（検証の偽陰性）

zsh はマッチしない glob があると `no matches found` で**コマンド全体を実行せず中断**する（`2>/dev/null` では防げない）。grep 検証に混ざると「マッチなし」と誤判定する。

- 存在が不確かなパスの glob は使わず、`grep -r <dir>/` でディレクトリ再帰にする。使うなら `setopt null_glob` か事前の存在確認をする。
- **「無し」と断定する前に、検証コマンド自体が実行されたか（エラー出力の有無）を確認する。**
- 同系統の罠：
  - `=` で始まる裸のワードは `=command` 展開される。区切り線は `echo "==="` とクォートするか `---` を使う。
  - **`GID` / `UID` / `EUID` / `EGID` をシェル変数に使わない**（特殊変数への代入で `failed to change group ID` となり中断する）。`SHEET_GID` のように接頭辞を付ける。
  - **引用符なしの変数はスペースで分割されない。** `for R in $(aws …)` とコマンド置換を直接書くか、`${=VAR}` と書く。
  - **`$VAR:` の直後に英字を続けない**（`:r` `:h` `:t` `:e` が修飾子になる）。ARN やパスは `${ACC}` と波括弧で括る。
  - `--include=*.md` のようなオプション値の glob はクォートする（`--include='*.md'`）。

## シンボリックリンクした設定ディレクトリの検索は静かに空振りする

`~/.claude/` 配下をシンボリックリンクで管理している場合、検索コマンドはリンクの扱いが実装ごとに違い、外すとエラーなしで終了コード1（＝該当なし）を返す。

| 検索の書き方 | `/usr/bin/grep -r` | `rg` |
|---|---|---|
| `~/.claude/AGENTS.md`（リンクの**ファイル**を引数指定） | ❌ 0件 | ✅ |
| `~/.claude/rules`（リンクの**ディレクトリ**。末尾スラッシュ無し） | ❌ 0件 | ✅ |
| `~/.claude/rules/`（末尾スラッシュあり） | ✅ | ✅ |
| `~/.claude/`（**リンクを含む親を再帰**） | ❌ 素通り | ❌ 素通り（`rg -L` なら読む） |

- **具体パスを引数に指定して `rg` で引く**のが既定。`~/.claude/` を丸ごと再帰するなら **`rg -L`**。最も確実なのはリンク先の実体を直接見ること。
- 対話シェルの `grep` がエイリアス等で置き換わっていると、非対話実行では `/usr/bin/grep` に解決されて結果が変わる。**`rg` に `--include` は無い**（`-g '*.md'` / `-t md` を使う）。
- **0件を「無い」の根拠にする前に、存在するはずの語で1回引いて、検索が対象を読んでいることを確かめる。**

## 複数作業の混線防止（CWD 干渉・ステージ範囲）

- Bash の並列実行間でも **working directory は共有される**。`cd` を使わず **`git -C <path>`** でリポを明示し、異なるリポの更新を同一メッセージで並列にしない。
- `git add -A` / `git add <dir>/` / `git add -u <dir>/` は**並行セッションの未コミットファイルを巻き込む**。対策の優先順：
  1. 自分が触ったファイルパスを明示列挙して add する
  2. `git commit <path> -m "..."` でパス指定コミット（**`git add` で明示列挙した場合に限る。`git apply --cached` で絞った直後には使わない**→下記）
  3. コミット前に `git status --short <dir>/` で目視。見覚えのないファイルは別セッションの作業
  4. `git add -A` / `git add <dir>/` / `git add -u <dir>/` は「自分しか触っていない」と確信できるときだけ
  5. 削除の stage も `git add <消したファイルの明示パス>` で足りる
- ⚠️ **複数セッションが同じファイルへ追記する「共有台帳ファイル」は、パスを明示列挙しても巻き込みを防げない。** 成果物の登録先 YAML・索引 `README.md` のほか、**ルール・設定ファイル（`CLAUDE.md` / `AGENTS.md` / `.claude/rules/*.md` / `SKILL.md`）も同じ扱いにする。** add の直前に `git diff <path>` を読んで自分の変更だけかを確かめる。混ざっていた場合、`git add -p` は対話式で使えないので、**`-U0` で変更行ごとに分割してから、自分の分だけ `git apply --cached` する**：

```bash
git diff -U0 <path> > /tmp/all.patch   # 文脈行なし＝変更行ごとに別のかたまりになる
# ヘッダー（--- / +++ まで）＋ 自分の変更のかたまりだけを抜き出して /tmp/mine.patch を作る
git apply --cached --unidiff-zero /tmp/mine.patch
git diff --cached <path>                # 自分の変更だけが stage されたか目で確認
```

⚠️ **既定の `git diff`（文脈3行）だと、近い行の変更が1つのかたまりに合流して分離できない**。必ず `-U0` と `--unidiff-zero` を使う。分離できなければ、そのファイルは**コミットせず相手に委ねる**。

⚠️ **`git apply --cached` の直後に `git commit <path> -m "..."` を打たない。** pathspec 付きの `git commit` は index を無視してワーキングツリーの内容をコミットするため、他セッションの未コミット分を巻き込む。**pathspec を付けない `git commit -m "..."`** を使う：

```bash
git apply --cached --unidiff-zero /tmp/mine.patch
git diff --cached <path>   # 自分の変更だけが stage されたか確認
git commit -m "..."        # ← ここで <path> を付けない
```

⚠️ **`git diff` での確認と `git add`〜`commit` を、同じ連結コマンド（`&&` つなぎ）に入れない。** diff は単独の呼び出しで実行し、出力を読んでから次の呼び出しで add する。

⚠️ **復元に相対リビジョン（`HEAD~1` / `HEAD^` / `@{1}`）を使わない。** 並行セッションのコミットで `HEAD` はずれている。`git log --oneline -5 -- <file>` でハッシュを確かめてから `git checkout <hash> -- <file>` を打つ。
